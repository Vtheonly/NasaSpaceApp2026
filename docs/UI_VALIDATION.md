# UI validation: map, burning calendar, anomalies, and forecast (issue #14)

## Scope and honest statement of what the UI is

The repository's user-facing viewer is `app/index.html`, generated by
`scripts/build_app.py` from the exported inference artifacts
(`calendar_forecast_records.csv`, `harmonized_daily.csv`,
`anomaly_records.csv`, and the inference `manifest.json`). It is a
**self-contained static page**: one HTML file, no server, no CDN, no external
requests of any kind - openable from disk (`file://`) on any modern browser,
which is what the offline/air-gapped project constraints require
(docs/ARCHITECTURE.md: "Run the user-facing app outside Kaggle").

This document is the usability validation record issue #14 asks for: the
declared target environments, the reviewer walkthrough, how each checklist
item is satisfied, and which items are covered by automated tests
(`tests/integration/test_app.py`, 42 tests) versus left for human review.
The committed demo page is built from the SYNTHETIC sample fixtures and is
labeled as such inside the page itself; a real-data run replaces it by
re-running the two commands at the bottom of this document.

## Declared target device/browser

- Primary: desktop/laptop, viewport >= 1280 px, current Chrome, Edge, or
  Firefox, macOS/Windows/Linux, keyboard + mouse.
- Secondary (smoke-level): tablet/mobile Safari/Chrome >= 360 px wide; the
  layout collapses via media queries, calendar cells shrink to 9 px, and
  every number remains available in text/ARIA form.
- Assistive tech spot-check: keyboard-only navigation is fully supported
  (Tab order: skip link -> header -> sections -> focusable year rows and
  SVGs); `:focus-visible` outlines are 3 px, contrast-checked.

The core demo is "completeable" on the primary target in well under five
minutes: open the file, skim the overview stats, hover year rows, read the
anomaly table, read the forecast status and chart, and check provenance.

## Reviewer walkthrough (core demo)

1. **Open** `app/index.html` (double-click; no server needed).
2. **Header** shows the AOI title, the series span, counts of observed vs.
   no-coverage days, anomaly counts, and the forecast status chip. If the
   inputs are fixtures, a prominent amber note says "SYNTHETIC DEMO DATA".
3. **Overview** section repeats the numbers as stat blocks.
4. **Hotspot map** plots every validated detection (circles = MODIS,
   triangles = VIIRS), with a coordinate grid and an explicit caption that
   detections are pixel centers, not exact fire locations.
5. **52-week-by-year burning calendar**: one row per year, one cell per ISO
   week (1..53), five activity levels, gray hatched cells for weeks with NO
   observed coverage (legend: "missing data, NOT zero activity"), dotted
   outlines for partially covered weeks, and per-year sensor-era labels
   (modis_only / modis+viirs / viirs_only). Tab to any year row and a
   screen-reader summary is announced (weeks, observed days, no-coverage
   days, summed activity, era).
6. **Anomaly details**: the top 12 days by absolute ratio with observed FRP,
   seasonal baseline, ratio, and status (high/low), each styled in AA
   contrast, with a caption explaining the definition.
7. **14-day forecast with uncertainty**: a status line states the model,
   horizon, and "experimental_uncalibrated" calibration; the chart shows the
   recent history, the median forecast (dashed), and the 10th-90th
   percentile band. When no forecaster was supplied, an explicit
   "No forecast available" status block replaces the chart - nothing is
   extrapolated silently.
8. **Provenance and limitations** lists the AOI, code commit, source files,
   input SHA-256 hashes (16-char prefixes), and the four standing
   limitations. The footer carries the required FIRMS/LANCE/ESDIS
   attribution.

## Known limitations of this validation (documented, not hidden)

1. **No interaction beyond inspection.** The page is a read-only viewer by
   design for the hackathon scope: AOI *selection* happens through the CLI
   (`--aoi`), not through the browser. Interactive AOI drawing on a basemap
   remains post-hackathon work (docs/POST_HACKATHON_BACKLOG.md), and the
   planned Streamlit host can embed these same artifacts.
2. **Human a11y audit still recommended.** Automated checks cover structure,
   labels, focus, contrast, and explicit states; a manual screen-reader pass
   (NVDA/VoiceOver) on the declared target is still advisable before final
   submission.
3. **No-forecast demo path is test-covered but not shipped as a second
   committed page**; regenerate locally with `--forecaster none` if you want
   to review that state in a browser.
4. The map is an honest scatter on a plain grid, not a tile basemap, because
   tile servers require network access, which the offline constraint forbids.

## Reproducing / regenerating

```bash
# 1. Full offline pipeline on the committed fixtures (~1 min, no network):
python3 scripts/run_pipeline.py --source-dir tests/fixtures/sample_aoi \
    --output-dir out --aoi "bbox:-123.5,39.5,-120.5,42.0" --seed 2026

# 2. Static app from the export (deterministic; committed copy = app/index.html):
python3 scripts/build_app.py --inference-dir out/inference \
    --source-dir tests/fixtures/sample_aoi --output-dir app \
    --generated-at "2026-10-22 00:00 UTC"

# 3. The usability/a11y contract suite:
python3 -m pytest tests/integration/test_app.py -q
```

`app_build.json` next to the page records input hashes, map point count,
forecast availability, the synthetic flag, and every palette contrast ratio -
the UI state is auditable exactly like the model artifacts.
